9. RC + EP 两卡并行

目录

  • 9.1 为什么是两进程而不是两线程
  • 9.2 用 CLI 一键并行
  • 9.3 批量文件：任务队列
  • 9.4 支持队列模式的模块
  • 9.5 自己写并行程序
  • 9.6 性能规律
  • 9.7 相关

同一张 Edge10 卡上，RC NPU 和 EP NPU 是两块独立算力。并行模式就是起 两个进程：一个跑 RC、一个跑 EP，把负载分给两边。

9.1 为什么是两进程而不是两线程

  • RC 和 EP 用的是两套互斥的驱动上下文（见 02_架构里的 /dev/ipcm0 冲突）。
  • 一个进程内同时初始化两套 DCL 会抢设备节点。
  • 所以 --rc-ep 实际上是 fork 两个进程，各自 Edge10Init 自己那套。

9.2 用 CLI 一键并行

edge10 入口已经封装好：

# 自动起一个 EP 进程 + 一个 RC 进程
edge10 --rc-ep flow_infer_ep -m models/onnx_resnet50.ty

它内部做的事：

EP_BIN=samples/bin/ep/flow_infer_ep
RC_BIN=samples/bin/rc/flow_infer_rc

( run_ep  $EP_BIN  $ARGS ) &    # mount namespace + EP env
( run_rc  $RC_BIN  $ARGS ) &    # 干净环境 + RC env
wait

9.3 批量文件：任务队列

传入多个文件时，--rc-ep 自动切换为任务队列模式：

  • RC 和 EP 各起一个 worker
  • 用 mv 原子操作从共享队列抢任务
  • 谁快谁多跑，自动适配两卡速度差
  • 用户只需一条命令，无需关心队列逻辑
# 6 个视频：RC 跑 4 个，EP 跑 2 个（自动均衡）
edge10 --rc-ep flow_video_codec_ep -i "videos/*.mp4" -o out/ \
       --ptype 265 --ptype-out 96 -w 1280 -h 720

# 10 张图：RC 跑 6 个，EP 跑 4 个
edge10 --rc-ep flow_classify_ep -m models/onnx_resnet50.ty \
       -i "images/*.jpg" -o out/ -w 1920 -h 1080

实测：

场景 全 RC 串行 队列（RC+EP） 加速
6 个 3s 视频 25.5s 18.0s 1.42x
8 张图 ~4s 3.9s ~1.0x

规律：任务耗时越长、数量越多，队列加速越明显。

  • EP 比 RC 慢约 2 倍（每次 API 调用走 PCIe RPC）
  • 短视频（<20s）EP 启动开销（~1.5s）占比大，加速有限
  • 长视频 + 多任务时收益最大

输出：所有结果直接写入 -o 目录，文件名不带 _rc/_ep。

9.4 支持队列模式的模块

  • flow_classify（多张图）
  • flow_yolo（多张图）
  • flow_video_codec（多个视频）
  • flow_video_track_detect（多个视频）

其他模块单文件时走"双进程同任务跑"，多文件时不支持队列。

9.5 自己写并行程序

业务侧不需要特殊 API。两个进程各自按 07_RC推理 和 08_EP推理 写即可，唯一区别是：

  • EP 进程必须用 Edge10-ep-run 或 edge10 --ep 启动。
  • RC 进程必须在"干净"环境下跑（不能有 EDGE10_SDK_CONFIG）。
  • 两个进程之间不共享 Edge10Executor / Context / Tensor，不要尝试跨进程传设备指针。

9.6 性能规律

配置 单次推理 备注
仅 RC ~10ms 小任务最快
仅 EP ~12ms 每次调用走 PCIe RPC
队列（RC + EP） 视任务而定 长任务/多任务并行优势大
